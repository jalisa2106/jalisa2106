DataMind

A local-first, self-correcting, RAG-augmented multi-agent framework for autonomous exploratory data analysis. It profiles a dataset, has an LLM propose research questions, writes and repairs analysis code in a network-isolated Docker sandbox, and turns verified output into grounded insights, charts and a PDF report. Every stage is logged, so the effect of retrieval can be measured, not guessed.

01 / OVERVIEW

What DataMind does

From raw upload to explained insight with minimal human input, while doubling as a controlled testbed for RAG vs. baseline question generation.

📁

Upload & Profile

CSV, TSV, JSON, Excel or Parquet via upload, URL, Kaggle or GitHub. A pandas profile is the only thing the LLM sees; raw data never leaves the machine.

🧠

Autonomous questioning

One LLM call per dataset proposes questions in six categories; a gatekeeper scores each 1–5 and drops anything below 3.

🔁

Self-correcting analysis

A LangGraph state machine writes code, runs it in Docker and rewrites it from the traceback (3 attempts). Success rises from 82.0% to 99.1%.

🔎

Switchable RAG

Schema-similarity retrieval over past insights feeds question generation only, so RAG is the single experimental variable.

📄

Insights, charts, report

Numerically grounded insights, up to three chart specs, a system-profile dashboard, and a Puppeteer-rendered PDF report with insights and charts.

📊

Measured per stage

Immutable per-trial JSONL telemetry plus offline LLM-judge scoring grade questions, code, insights and cost.

02 / SYSTEM ARCHITECTURE

FastAPI backend, Next.js frontend, local-first AI

A LangGraph agent graph owns the reasoning loop, FastAPI owns persistence and orchestration, and local ChromaDB gives zero-cost RAG, with Docker isolating untrusted code and Gemini as the supported LLM.

🧭 The one architectural rule

question_generator sits outside the per-run graph: it runs once per dataset, while the compiled graph runs once per research question, so “generate N questions” state never mixes with “answer 1 question” state. Every category, including the system_profile dashboard question, goes through code_generator and the sandbox with no bypass.

03 / DATA FLOW

Dataset lifecycle, end to end

The canonical path a dataset travels from upload to a downloadable report.

STEP 1

Upload & Ingest

File, URL or Kaggle API; raw file persisted, Dataset row created.

STEP 2

Profiling

Schema, stats, correlation summaries and a bounded row sample → DatasetProfile.

STEP 3

Question generation

One LLM call per dataset over six categories; RAG may ground it; scorer drops < 3.

STEP 4

Per-question run

An AnalysisRun starts the LangGraph pipeline; code_generator writes pandas code.

STEP 5

Sandbox & self-correction

Fresh container per attempt; on failure code_corrector rewrites until success or max_attempts.

STEP 6

Result analysis

Deterministic stdout truncation and sanitizing.

STEP 7

Insight & visualization

Narrative insight plus chart metadata; PNG comes from the sandboxed script.

STEP 8

RAG indexing

Insight embedded on the dataset’s schema text; best-effort.

STEP 9

Report & export

Markdown report → Puppeteer A4 PDF containing insights and visualizations; each run appends to a JSONL trial log.

06 / MODULES & AGENT NODES

7 graph nodes plus 2 pre-graph agents

Each node is a focused async function over a shared AnalysisState; LLM nodes load prompts from markdown files under app/agents/prompts/.

01

question_generator

Runs once per dataset, from POST /datasets/{id}/questions. Produces a structured question batch across six categories with target columns and rationale.

01b

rq_quality_scorer

Gatekeeper: one structured LLM call scores each question 1–5; anything below 3 is dropped in both experiment arms.

02

code_generator

First node of the per-run graph. Writes pandas code from the question, profile context and, optionally, retrieved past insights.

03

sandbox_execute

Runs code in Docker (--network none, --cap-drop ALL, no-new-privileges, tmpfs) and captures stdout/stderr, exit code, duration and output files.

04

route_after_execution

Success → result_analyzer; failure with attempts left → code_corrector; exhausted → give_up (run marked failed, last stderr stored).

05

code_corrector

Rewrites failing code from its traceback, appends to code_history and loops back — bounded by max_attempts.

06

result_analyzer

Deterministic, no LLM. Truncates and sanitizes stdout so downstream calls get bounded, clean input.

07

insight_writer

Writes summary, takeaways and a confidence score; forbidden from using numbers absent from stdout.

08

visualization_builder

Asks the LLM only for chart metadata (type, title, labels); the PNG is rendered by the sandboxed script. Skipped if no chart exists.

09

RAG store

Local persistent ChromaDB with all-MiniLM-L6-v2 embeddings: zero API tokens; an RLock guards init.

10

RAG retriever

Top-5 similar past records by cosine similarity, excluding the query dataset (audit: 0.0% leakage). Inspiration only.

11

RAG indexer

Indexes each successful insight, best-effort: failure never fails the run.

12

Dataset Fetch Service

Direct URL or Kaggle API, normalized to one raw-dataset form.

13

LLM Provider Factory

get_llm with per-node provider:model specs (default google:gemini-3.1-flash-lite, temp 0.2) plus tenacity retry.

🔐 Auth

Local single-user JWT login; weak secrets rejected outside dev.

📡 Live status

Token-auth WebSocket from an in-process pub/sub bus; UI also polls.

📊 Run metrics

Per-node token/call counts and retry counts feed RAG-vs-baseline.

📄 PDF report export

One executive PDF with the summary, per-question insights, takeaways and charts.

10 / EVALUATION

Grading every stage, not just the answer

Paired design: 24 datasets × 2 arms (Baseline vs RAG), same model, temperature 0.2, 3 attempts, 60 s timeout. Retrieval is confined to question_generator, so it is the only variable.

❓ Question quality

Column grounding, category coverage, redundancy (cosine > 0.80), diversity; relevance, specificity, actionability (1–5) from an offline LLM judge.

💻 Code quality

FPSR, ESR, mean attempts, latency, static signals and a 5-dimension rubric (0.20 each).

💡 Insight & cost

Numerical faithfulness, groundedness, Flesch–Kincaid, caveats, tokens per insight, calls, latency, failure taxonomy.

🧪 Method

24 datasets sampled from 134 public sets across 29 domains (569–32.4M rows, 4–40 cols); 2 arms; 48 batches; 322 trials. The vector store held 78 deduplicated insights, frozen during runs. Two-sided Wilcoxon signed-rank on per-dataset means (n=24), Holm–Bonferroni over 29 metrics, 95% bootstrap CIs (B=10,000). Judging is offline over the append-only log. Reproduce: seed_datasets.py → experiment.run_experiment → judge_trials → analyze_results.

H1 · Not supported

RAG scored higher on average, but nothing survived correction. Relevance improved on 11 of 24 datasets (tied 8, lower 5); dz 0.24–0.28.

H2 · Holds on cost

Small, prompt-driven token rise (question gen +4.2%, insight writing +13.5%) with no quality gain to offset it.

H3 · Partly supported

No harm to grounding or faithfulness and self-correction recovered most failures, but retrieval significantly lowered first-pass success.

⚠ Limitations & future work

The judge shares a model with the generator and has no human calibration. With n=24, one batch per arm and no repeats, tests are underpowered; scope is 24 public datasets, a 78-insight corpus and one low-cost model. The 1 GB / 60 s sandbox strains the largest sets (two Bitcoin first attempts timed out, then self-corrected). Next: retrieve successful code snippets, human review of questions, stronger models, multi-table data, multiple judges.
